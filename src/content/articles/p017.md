# AI Agent 落地实战：从架构设计到知识库建设，我踩过的那些坑

上周的一个深夜，我盯着会议纪要发呆。

团队花了三周时间讨论 AI Agent 的架构设计，从主控 Agent 到子 Agent，从 Skill 到 Tool，从 RAG 到向量库……概念一大堆，PPT 画了几十页，但真正落地的代码？还是零。

这让我想起一个残酷的事实：**90% 的 AI 项目死在了「从 Demo 到生产」这一步。**

今天，我想分享一下最近几个月在企业里推动 AI Agent 落地的真实经历。不是什么高大上的方法论，而是实实在在踩过的坑、做过的决策、以及一些或许能帮到你的思考。

---

## 一、先搞清楚一件事：AI Agent 到底要解决什么问题？

很多团队一上来就讨论技术架构：用 LangChain 还是自研？主控 Agent 怎么设计？记忆模块怎么做？

**这都是错的。**

在我们团队的一次会议上，产品同学抛出了一个灵魂拷问：

> "我们做的这个 Agent，到底要帮用户解决什么问题？"

全场沉默。

技术侧能说出一堆：意图识别、槽位填充、工具调用、RAG 召回……但这些都是手段，不是目的。

后来我们花了整整两天，只做一件事：**把 30 个真实业务场景写下来，逐个分析用户到底需要什么。**

比如，内容运营团队的真实需求是：

1. 每天从 TikTok 热榜找到和火车旅行相关的爆款话题
2. 看到话题后，想知道"这个话题为什么火"
3. 基于洞察，快速生成一个可落地的脚本

注意，他们要的不是"一个能聊天的 AI"，而是**一套能缩短工作流程的工具链**。

这个认知转变，让我们后续的架构设计清晰了很多。

## 二、架构设计：别被"多 Agent"迷惑了

市面上很多文章都在鼓吹"多 Agent 协作"、"Agent Swarm"，好像不用多 Agent 就落后了。

但在实际落地中，我发现一个残酷的真相：

**Multi-Agent 架构在大多数企业场景下是过度设计。**

为什么？

我们曾经尝试过把一个内容生产工具拆成多个 Agent：选题 Agent、脚本 Agent、审核 Agent、发布 Agent……

结果呢？

- Agent 之间的"打架"问题层出不穷——一个 Agent 说"这个话题好"，另一个说"不符合合规要求"，用户完全懵了
- 调度成本急剧上升——原本一个 API 调用能完成的事，现在需要四五次
- 调试难度指数级增加——出了问题根本不知道是哪个 Agent 的锅

后来我们改成了一个更简单的架构：

```
用户输入
    ↓
主控 Agent（意图识别 + 任务规划）
    ↓
根据意图调用对应的 Skill/Tool
    ↓
返回结果
```

**核心原则：能用 Skill 解决的问题，不要拆成多个 Agent。**

什么是 Skill？简单说就是**封装好的能力模块**——一段 Prompt 加一段 Python 代码，能完成一个独立的小任务。比如"抓取 TikTok 热榜"、"生成脚本大纲"、"检查合规红线"。

这些 Skill 不需要有自己的"思考能力"，它们就是工具。主控 Agent 负责理解用户意图、规划任务、调度 Skill，最后汇总结果。

这个架构有几个好处：

1. **调试简单**——出问题了，先看主控 Agent 的意图识别对不对，再看调用的 Skill 执行结果对不对
2. **迭代灵活**——新增能力只需要加一个 Skill，不用改架构
3. **成本可控**——每个 Skill 的 Token 消耗是固定的，不会因为"Agent 之间对话"而失控

## 三、知识库建设：这才是 AI Agent 的命门

说完架构，聊聊另一个关键问题：**知识库**。

我见过太多团队在这个环节翻车。要么是"全量向量化"导致召回不准，要么是"知识库空空"导致 AI 只会胡说八道。

在我们的项目中，知识库建设经历了三个阶段。

### 第一阶段：什么都往里塞

一开始，大家的想法很简单：把所有文档都扔进向量库，让 AI 自己去找。

结果？灾难。

用户问"火车票怎么退票"，AI 召回了一堆八竿子打不着的内容——什么"火车站附近酒店推荐"、"火车旅行攻略"……

问题出在哪？

**向量相似度不等于语义相关度。**

"火车票退票"和"火车旅行攻略"在向量空间里可能很近，但对用户来说完全是两回事。

### 第二阶段：分层索引

后来我们借鉴了一个简单的思路：**像图书馆一样管理知识库**。

图书馆有分类目录，用户先找到"交通出行"这个大类，再找到"火车票"这个子类，最后找到"退票政策"这本书。

我们的知识库也这么设计：

```
知识库/
├── 业务背景/        # 公司介绍、业务逻辑
├── 内容创作/        # 爆款方法论、脚本模板
│   ├── 爆款方法论/
│   ├── 脚本库/
│   └── 审核红线/
├── 账号运营/        # 平台规则、运营数据
└── 常见问题/        # FAQ、客服话术
```

AI 在召回时，先判断用户问题属于哪个类别，再在对应类别下做向量检索。

这一步优化后，问答准确率从 75% 提升到了 85%。

### 第三阶段：分层存储 + 差异化策略

但 85% 还不够。

我们发现不同类型的知识，需要不同的处理策略：

| 知识类型 | 特点 | 处理策略 |
|---------|------|---------|
| 定价规则 | 变化少，结构化 | 存结构化表格，精确匹配 |
| 平台政策 | 变化快，时效性强 | API 实时查询 + 知识库兜底 |
| 爆款方法论 | 高频引用，需要精准 | 单独整理，设为高优召回 |
| FAQ | 量大，覆盖长尾 | 向量召回，粗排精排 |

比如限行政策这种时效性强的内容，我们不放在知识库里，而是直接调用交管部门的 API。知识库只作为兜底，并且会明确标注"信息可能过时，请以官方为准"。

**核心原则：知识库不是越全越好，而是越准越好。**

## 四、评测体系：别只看"准确率"

很多团队在做 AI 评测时，只看一个指标：准确率。

这是不够的。

在打车 Agent 项目中，我们设计了一套分层评测体系：

**北极星指标：任务完成率**
- 用户说"帮我叫个车去机场"，最终是否成功叫到车？

**业务指标：**
- 意图识别准确率
- 工具调用成功率
- 响应延迟

**用户行为指标：**
- 重复提问率（越低越好）
- 重新生成率（越低越好）
- 投诉率

为什么要看用户行为指标？

因为**准确率 80% 和用户体验好是两回事**。

比如，AI 有 20% 的概率识别错意图。如果每次出错都让用户重新说一遍，用户体验会很差。但如果 AI 能在不确定时主动确认——"您是要去浦东机场还是虹桥机场？"——用户反而会觉得这个 AI 很聪明。

所以我们在意图识别环节加入了置信度分级：

- 置信度 > 90%：直接执行
- 置信度 70-90%：弱确认，3 秒无异议默认通过
- 置信度 60-70%：明确确认，提供选项
- 置信度 < 60%：请用户澄清

这套机制上线后，虽然"首次直接成功率"下降了，但"最终任务完成率"反而提升了。

## 五、一些血泪教训

最后分享几个踩坑经验：

### 1. 别一上来就追求"全自动"

很多老板都想要"全自动"——用户说一句话，AI 自动完成所有事情，人完全不用参与。

这在大多数场景下是不现实的。

更务实的做法是：**先做"半自动"，跑通后再逐步提升自动化程度。**

比如内容审核，一开始我们让 AI 做初筛，标记出可能有问题的内容，人工做最终判断。等积累了足够多的数据和规则后，再逐步提升 AI 自动通过的比例。

### 2. 知识库需要持续维护

很多团队把知识库当成"一次性工程"——搭建完就不管了。

但业务在变，规则在变，知识库也需要跟着变。

我们的做法是：**每月一次 Review，由业务方 + 产品 + 技术一起检查知识库的时效性和准确性。**

### 3. 先验证需求，再做技术

这是最重要的一点。

在做 AI 产品之前，一定要先验证：**这个需求是真实存在的，还是我们臆想出来的？**

很多时候，业务方说"我需要一个 AI 帮我写脚本"，但实际上他真正的痛点可能是"找不到好的选题"。如果我们一上来就做脚本生成，可能做了半天发现用户根本不用。

## 写在最后

AI Agent 落地，本质上不是一个技术问题，而是一个产品问题、组织问题。

技术架构可以抄，但**对业务的理解、对用户需求的洞察**，是抄不来的。

与其追求"多么先进的 Agent 架构"，不如先想清楚：

1. 用户到底要解决什么问题？
2. AI 能在哪个环节创造价值？
3. 如何设计一套能持续迭代的机制？

这些问题想清楚了，技术自然就清晰了。
