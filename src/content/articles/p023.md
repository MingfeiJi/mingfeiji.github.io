# RAG 召回准确率从 65% 到 92%：我在大厂踩过的 7 个坑

上个月，我们的客服 AI 被投诉了 47 次。

投诉内容高度一致：答非所问。

用户问「怎么退票」，AI 回答「如何改签」。
用户问「价格是多少」，AI 回答「如何支付」。
用户问「能不能带宠物」，AI 回答「行李额度规定」。

我们排查了一周，问题不在大模型。GPT-4 的理解能力没问题。

问题出在 RAG 的召回环节。

我们从知识库里捞出来的内容，根本不是用户想要的。大模型再聪明，给它喂错的上下文，它也只能基于错误的信息生成回答。

这篇文章记录我们把 RAG 召回准确率从 65% 提升到 92% 的完整过程。不讲理论，只讲我们实际做了什么、踩了哪些坑、怎么解决的。

---

## 一、先说清楚问题：RAG 的召回到底在干什么

RAG 的全称是 Retrieval-Augmented Generation，检索增强生成。

核心逻辑很简单：

```
用户问题 → 从知识库里检索相关内容 → 把检索到的内容喂给大模型 → 大模型基于这些内容生成回答
```

这个流程里有三个环节可能出问题：

1. **检索环节**：从知识库里捞出来的内容不对
2. **生成环节**：大模型理解错了或者表达不好
3. **知识库本身**：内容就是错的或者过时的

我们的问题主要出在第一个环节：检索。

检索的核心指标叫「召回准确率」。简单说就是：在所有检索出来的内容里，有多少是真正和用户问题相关的。

我们最初的召回准确率只有 65%。意思是：每检索 10 条内容，只有 6.5 条是相关的，剩下 3.5 条是干扰项。

大模型看到这 3.5 条干扰项，就可能被带偏。

---

## 二、我们最初的方案：最简单的向量检索

我们最初的方案非常教科书：

1. 把知识库的文档切成 chunk，每个 chunk 500 字左右
2. 用 OpenAI 的 text-embedding-ada-002 把每个 chunk 向量化
3. 存到 Pinecone 向量数据库
4. 用户问问题时，把问题也向量化，然后做相似度检索，取 Top 5

这个方案是 RAG 的标准做法。网上 90% 的教程都是这么教的。

但实际跑下来，效果很差。

我们做了一个测试集，包含 200 个真实用户问题，每个问题人工标注了「正确答案应该来自哪个文档」。

测试结果：
- Top 1 命中率：42%
- Top 5 命中率：65%

也就是说，有 35% 的问题，正确答案根本没出现在召回的 5 条内容里。

---

## 三、第一个坑：Embedding 模型选错了

我们最初用的是 OpenAI 的 text-embedding-ada-002。

这个模型是通用模型，在通用场景下表现不错。但我们的场景是「客服知识库」，涉及大量专业术语和业务场景。

我做了一个实验：

用同样的 200 个问题，分别用不同的 Embedding 模型测试召回准确率：

| 模型 | Top 5 召回准确率 |
|------|------------------|
| text-embedding-ada-002 | 65% |
| text-embedding-3-large | 71% |
| bge-large-zh-v1.5 | 74% |
| 自己微调的 bge | 82% |

结论很明显：**换一个更好的 Embedding 模型，能直接提升 6-9 个百分点**。

但更大的提升来自「微调」。

我们用业务数据微调了 bge-large-zh-v1.5。微调数据是这样的：

```json
{
  "query": "怎么退票",
  "positive": "退票流程说明：登录账户后，进入订单详情页，点击退票按钮...",
  "negative": "改签流程说明：如需更改出行日期，请登录账户..."
}
```

用了 5000 条这样的数据做微调，召回准确率从 74% 提升到 82%。

**我的判断是：Embedding 微调是 ROI 最高的优化手段之一。** 5000 条数据，微调成本不高，但效果提升明显。

---

## 四、第二个坑：分块策略太粗暴

我们最初的分块策略是「固定 500 字一块」。

这个策略有两个问题：

### 问题 1：语义被切断

比如一个完整的「退票政策说明」有 800 字，被切成两块：

- 第一块：退票政策的前半部分（讲什么情况可以退）
- 第二块：退票政策的后半部分（讲退票手续费）

用户问「退票手续费怎么算」，检索到第二块，但第二块缺少上下文，大模型可能理解不完整。

### 问题 2：粒度不一致

有些知识点只需要 100 字就能说清楚，硬凑成 500 字就会引入噪音。
有些知识点需要 1000 字才能说清楚，切成两块就会丢失完整性。

**我们后来改成了「语义分块」**：

1. 先用标题层级做初步切分（一级标题、二级标题）
2. 每个分块保持语义完整性，不硬切
3. 分块长度控制在 200-800 字之间
4. 每个分块带上父级标题作为上下文

分块方式改完之后，召回准确率从 82% 提升到 86%。

具体实现用的是 LangChain 的 RecursiveCharacterTextSplitter，配合自定义的标题检测逻辑。

---

## 五、第三个坑：只用向量检索

向量检索的原理是「语义相似度」。

但语义相似不等于问题相关。

举个例子：

用户问：「北京到上海的票价是多少」

向量检索可能召回：
- 「上海到杭州的票价是多少」（语义很相似，但城市错了）
- 「北京到上海的行程时间」（城市对了，但问的不是票价）

这两条在向量空间里和用户问题都很「近」，但都不是正确答案。

**我们的解决方案是「混合检索」**：向量检索 + 关键词检索。

具体做法：

1. 向量检索召回 Top 20
2. BM25 关键词检索召回 Top 20
3. 用 RRF（Reciprocal Rank Fusion）算法融合两个结果
4. 取融合后的 Top 5

BM25 是经典的关键词检索算法，它会严格匹配「北京」「上海」「票价」这些关键词。

混合检索上线后，召回准确率从 86% 提升到 89%。

**我发现一个规律**：用户问题越具体（包含地名、产品名、时间等实体），关键词检索的价值越大。用户问题越抽象（「怎么办」「为什么」），向量检索的价值越大。

---

## 六、第四个坑：没有做意图分类

我们的知识库有几千篇文档，覆盖十几个业务场景：

- 订票流程
- 退票流程
- 改签流程
- 价格政策
- 行李规定
- 会员权益
- ...

用户问「怎么退票」，全库检索会把「改签流程」「价格政策」这些内容也召回来，因为它们在向量空间里也挺近的。

**我们加了一层「意图分类」**：

```
用户问题 → 意图分类 → 只在对应类目下检索
```

意图分类用的是一个简单的分类模型，准确率 95% 左右。

比如用户问「怎么退票」，意图分类判断是「退票相关」，然后只在「退票」类目下做检索。

这一步把检索范围从几千篇缩小到几百篇，干扰项大幅减少。

召回准确率从 89% 提升到 91%。

---

## 七、第五个坑：Query 质量太差

用户的问题经常是模糊的、口语化的、甚至是错别字的。

比如：
- 「那个怎么弄」（指代不明）
- 「piao怎么退」（拼音）
- 「改钱」（错别字，想问改签）

直接拿这些 query 去检索，效果肯定差。

**我们做了「Query 改写」**：

```
原始 Query → 大模型改写 → 改写后的 Query → 检索
```

改写的目标是：
1. 补充上下文（根据对话历史）
2. 纠正错别字
3. 把口语化表达转成规范表达
4. 拆解复合问题

举个例子：

```
用户第一句：我买了张票
用户第二句：那个怎么退

改写后：如何退票
```

改写用的是 GPT-3.5-turbo，成本很低，延迟也可接受（100ms 左右）。

Query 改写上线后，召回准确率从 91% 提升到 92%。

---

## 八、第六个坑：没有做 Rerank

即使召回的 5 条内容都相关，它们的相关程度也是不一样的。

向量相似度的排序不一定准确。有时候相似度第三的内容，其实比第一的更相关。

**我们加了一个 Rerank 模型**：

```
召回 Top 10 → Rerank 模型重排 → 取 Top 5
```

Rerank 模型用的是 Cohere 的 rerank-multilingual-v2.0。

它的原理是：把 query 和每个候选文档一起输入，让模型判断「这个文档对回答这个问题有多大帮助」，得到一个相关性分数，然后按分数重排。

Rerank 的效果很明显，特别是在「Top 1 命中率」上：

| 指标 | Rerank 前 | Rerank 后 |
|------|-----------|-----------|
| Top 1 命中率 | 71% | 83% |
| Top 5 命中率 | 92% | 94% |

Top 1 命中率从 71% 提升到 83%，意味着更多情况下，最相关的内容排在第一位。这对大模型生成回答的质量影响很大。

---

## 九、第七个坑：知识库本身有问题

前面讲的都是检索策略的优化。但有一个更底层的问题：**知识库本身的质量**。

我们发现知识库有几个问题：

### 问题 1：内容过时

有些政策已经变了，但知识库里还是旧的。用户问的是新政策，AI 回答的是旧政策。

### 问题 2：内容冲突

同一个问题，知识库里有多个版本的回答，而且互相矛盾。检索到哪个取决于运气。

### 问题 3：内容缺失

有些用户常问的问题，知识库里根本没有对应的内容。

**我们做了几件事来改善**：

1. **建立知识库更新机制**：政策变化后 24 小时内必须更新知识库
2. **去重和冲突检测**：用向量相似度找到内容重复的文档，人工审核合并
3. **补全缺失内容**：分析用户问题日志，找出知识库没覆盖的高频问题，补充内容

知识库质量提升后，整体效果又有了明显改善。

## 十、最终效果和关键数据

经过这一系列优化，我们的 RAG 召回效果是这样的：

| 优化阶段 | Top 5 召回准确率 | 主要改动 |
|----------|------------------|----------|
| 基线 | 65% | 标准方案 |
| 换 Embedding | 71% | ada-002 → 3-large |
| 微调 Embedding | 82% | 业务数据微调 bge |
| 语义分块 | 86% | 固定长度 → 语义分块 |
| 混合检索 | 89% | 加入 BM25 |
| 意图分类 | 91% | 先分类再检索 |
| Query 改写 | 92% | GPT 改写 query |
| Rerank | 94% | Cohere rerank |

从 65% 到 94%，提升了 29 个百分点。

反映到业务指标上：
- 用户投诉率从 2.3% 降到 0.4%
- 人工介入率从 38% 降到 15%
- 平均对话轮次从 4.2 轮降到 2.1 轮

## 十一、我总结的几个方法论

做完这个项目，我有几个认知上的收获。

### 1. Embedding 是基础，但不是全部

很多人觉得 RAG 效果不好，第一反应是「换个更好的 Embedding 模型」。

Embedding 确实重要，但它只是众多环节之一。我们的提升里，Embedding 微调贡献了 11 个百分点（65%→82% 中的大部分），但后面的策略优化又贡献了 12 个百分点。

**不要指望一个模型解决所有问题。**

### 2. 检索是个工程问题，不是算法问题

RAG 优化的核心不是「找到最好的算法」，而是「把多个策略组合好」。

混合检索、意图分类、Query 改写、Rerank，每个单独看都不复杂，但组合起来效果就很好。

**这是个工程问题，需要脏活累活。**

### 3. 数据质量 > 模型能力

知识库内容本身有问题，再好的检索策略也没用。

我们有一次花了两周优化检索策略，效果提升不明显。后来发现是知识库里有大量过时内容，清理完之后效果立刻改善。

**垃圾进，垃圾出。这个道理在 RAG 里特别明显。**

### 4. 要有评测体系

没有评测，就不知道优化有没有效果。

我们建立了一个 200 题的测试集，每次改动都跑一遍，看召回准确率是升了还是降了。

**没有度量就没有改进。**

## 十二、一些具体的实现建议

如果你也在做 RAG 优化，这是我的建议优先级：

### 第一优先级：建立评测体系

先搞清楚现在的效果是多少，不然后面的优化都是盲人摸象。

评测集不需要很大，100-200 个问题就够了。关键是要覆盖主要场景，而且要有人工标注的正确答案。

### 第二优先级：检查知识库质量

先确保知识库内容是对的、是全的、是新的。这个比优化检索策略更重要。

### 第三优先级：混合检索

向量检索 + BM25，这个组合几乎是必做的。实现成本不高，效果提升明显。

### 第四优先级：微调 Embedding

如果你有业务数据，微调 Embedding 的 ROI 很高。5000 条数据就能看到明显效果。

### 第五优先级：Rerank

如果追求更高的准确率，加一个 Rerank 模型。但这会增加延迟和成本，需要权衡。

RAG 看起来简单，做好很难。

我们做了三个月，从 65% 到 94%，中间踩了无数的坑。这篇文章只记录了主要的几个。

**我的核心认知是：RAG 不是一个算法问题，是一个系统工程问题。**

不存在一个「最优方案」能解决所有问题。你需要根据自己的业务场景，把多个策略组合起来，然后不断迭代。

如果你也在做 RAG，希望这些经验对你有帮助。
