故事是这样的。

半年前我们开始做 AI Agent 系统，第一件事就是调研市面上的开源框架。

AutoGPT、CrewAI、LangGraph、MetaGPT，能找到的都测了一遍。

测完之后做了一个决定，全放弃，自己搭。

这个决定在当时团队内部是有争议的。用开源框架多省事啊，为什么要自己造轮子？

跑了半年之后回头看，这可能是我们做对的最重要的一个决策。

这篇文章记录一下我们为什么放弃开源框架，以及自己搭的系统是怎么设计的。

---

先说说我们测试开源框架的过程。

第一个测的是 AutoGPT。

当时这个项目 star 数最多，名气最大。我们想的是，这么多人用，应该靠谱。

实际跑下来发现几个问题。

第一个问题是不可控。AutoGPT 的设计理念是「自主」，给它一个目标，让它自己想办法完成。听起来很美，实际上在生产环境里完全不能用。

我们测试的场景是自动写视频脚本。给 AutoGPT 一个主题，让它输出脚本。

它会自己搜索资料、分析竞品、整理大纲、写初稿。流程看起来很完整。

问题是，每次跑出来的结果都不一样。有时候它会花大量时间在搜索上，搜着搜着跑偏了。有时候它会跳过某些步骤，直接给一个很粗糙的结果。

作为演示很酷炫，作为产品完全不行。

第二个问题是成本。自主决策意味着大量的思考和反思步骤，token 消耗是确定性流程的 5 到 8 倍。我们算了一下，如果上线，光 API 成本就顶不住。

第三个问题是调试困难。出了问题，你很难定位是哪一步出的问题。因为每一步都是 AI 自己决定的，没有固定的流程可以追溯。

---

第二个测的是 CrewAI。

CrewAI 的思路是多个 Agent 协作，每个 Agent 有自己的角色和职责。比如一个负责调研，一个负责写作，一个负责审核。

这个思路比 AutoGPT 好一些，至少有了分工。

但跑下来还是有问题。

第一个问题是 Agent 之间的通信很乱。Agent A 调用 Agent B，Agent B 又调用 Agent C，调用链一长，你根本不知道中间发生了什么。一旦某个环节出错，整个链路就崩了。

第二个问题是职责边界模糊。「调研 Agent」到底应该做到什么程度？是只搜索，还是要做初步筛选？是输出原始资料，还是要整理成结构化的格式？这些边界框架没有定义，全靠你自己设计。

第三个问题是难以复用。每个项目的需求不一样，Agent 的配置也不一样。换一个场景就要重新设计一套 Agent 角色和协作流程。

---

第三个测的是 LangGraph。

LangGraph 的设计理念我其实比较认同，用图的方式来定义 Agent 的状态流转。相比前两个，它更接近工程化思维。

但问题是太复杂了。

为了实现一个简单的工作流，你需要定义节点、定义边、定义状态、定义条件跳转。代码量一上来，可读性就没了。

更麻烦的是，业务逻辑和框架代码混在一起。想改一个业务规则，要在一堆 Python 代码里翻来翻去。

对于工程师来说这还能接受，但我们团队还有运营同学，他们也需要调整业务规则。让他们改 Python 代码是不现实的。

---

测完三个主流框架，我们总结了几个共性问题。

第一，控制力不足。这些框架都希望 AI 能「聪明」一点，自己做决策。但在生产环境里，我们需要的是可预测，不是聪明。

第二，耦合度太高。业务逻辑和框架代码混在一起，改动成本高，复用性差。

第三，调试困难。出了问题不知道从哪里下手。

第四，学习成本高。每个框架都有自己的概念和抽象，团队需要花时间学习。而且框架版本迭代快，今天学会的东西明天可能就变了。

---

想清楚这些问题之后，我们开始设计自己的方案。

核心思路是八个字，确定性骨架，灵活内核。

什么意思呢。

骨架是确定的。任务分解、执行顺序、数据流转、错误处理，这些都是固定的，写死在代码里。不管 AI 怎么想，流程就是这样走。

内核是灵活的。每个具体的处理步骤，用大模型来做。比如「根据热点生成选题」、「把大纲扩写成脚本」，这些事情让 AI 发挥创造力。

换句话说，我们不让 AI 决定「做什么」，只让 AI 决定「怎么做」。

---

具体怎么设计的呢。

我们的系统有三层。

第一层是编排层。这一层是确定性的，用代码写死。它定义了任务的执行顺序，A 做完了才能做 B，B 做完了才能做 C。这一层完全没有 AI，就是普通的程序逻辑。

第二层是技能层。每个技能对应一个具体的能力，比如「热点抓取」「竞品分析」「脚本生成」。技能是独立的模块，可以单独测试、单独迭代。

第三层是工具层。技能会调用工具来完成具体操作，比如调用搜索 API、读写数据库、生成图片。工具是最底层的原子操作。

三层分开，各管各的事。

---

说说每一层的具体实现。

编排层我们用的是最简单的方案，Markdown 文件。

是的，就是 Markdown。

我们在一个 .md 文件里定义任务的执行流程。类似这样。

任务开始，执行热点抓取技能，拿到热点列表。然后执行选题生成技能，根据热点生成选题。然后执行脚本大纲技能，生成大纲。然后执行脚本生成技能，生成完整脚本。任务结束。

就这么简单。

为什么用 Markdown？因为 Markdown 可以直接被大模型读懂。我们把这个文件作为系统 Prompt 的一部分，大模型就知道整个流程是什么，当前执行到哪一步。

另一个好处是，运营同学也能看懂，也能改。不需要懂代码。

---

技能层的设计也很简单。

每个技能是一个独立的 Markdown 文件，里面定义了这个技能的名称、描述、输入输出格式、具体的 Prompt。

比如「选题生成」技能的定义是这样的。

技能名称，选题生成。技能描述，根据热点列表和品牌调性生成视频选题。输入格式，热点列表是 JSON 数组，品牌调性是文本描述。输出格式，选题列表是 JSON 数组，每个选题包含标题、角度、预估热度。然后是具体的 Prompt 模板。

技能文件不包含任何代码逻辑。它就是一个说明文档，告诉系统这个技能是干什么的、怎么调用。

---

工具层是唯一有代码的地方。

每个工具是一个 Python 函数，做一件具体的事。比如 search_web 搜索网页，read_file 读取文件，call_api 调用外部接口。

我们有一个原则，每个工具不超过 50 行代码，不包含任何业务逻辑。

工具只做原子操作，不做业务判断。判断的事情交给上层的技能或者编排层。

这样做的好处是，工具可以高度复用。同一个 search_web 工具，热点抓取技能在用，竞品分析技能也在用，脚本审核技能也在用。

---

说说这个设计解决了哪些问题。

第一，可控性。编排层是确定的，我们知道任务会按照什么顺序执行。AI 只在技能层发挥作用，不会跑偏。

第二，可调试。每一层都是独立的，出了问题可以快速定位。是编排层的顺序问题，还是技能层的 Prompt 问题，还是工具层的接口问题，一目了然。

第三，可迭代。想优化某个技能，直接改那个技能的 Markdown 文件就行，不影响其他部分。想加一个新工具，写一个 50 行的函数就行。

第四，可协作。运营同学可以改技能的 Prompt，工程师可以加新工具，产品经理可以调整编排流程。各自干各自的事。

---

讲一个实际的例子。

上个月我们接到一个需求，要在脚本生成后增加一个「敏感词检测」的环节。

如果用开源框架，可能需要改好几个地方，重新定义 Agent 角色，调整协作流程，可能还要升级框架版本。

用我们的方案，改动是这样的。

第一步，在工具层加一个 check_sensitive_words 工具，调用敏感词库 API，返回检测结果。30 行代码。

第二步，在技能层加一个「敏感词检测」技能，定义输入是脚本文本，输出是检测结果和修改建议。一个 Markdown 文件。

第三步，在编排层的流程里，在「脚本生成」后面加一行，执行敏感词检测技能。

整个改动花了不到两小时，当天就上线了。

---

说说我们踩过的坑。

第一个坑是技能粒度太粗。

一开始我们设计了一个「内容生产」技能，把选题、大纲、脚本、审核全包进去。结果这个技能的 Prompt 超长，效果也不稳定。

后来拆成四个独立的技能，每个技能只做一件事，效果立刻好了。

经验是，一个技能只解决一个问题。如果你发现 Prompt 超过 500 字，可能就该拆了。

第二个坑是工具太智能。

一开始有个同学写了一个「智能搜索」工具，会自己判断搜索什么关键词、用哪个搜索引擎、怎么过滤结果。

结果这个工具不稳定，有时候搜出来的东西不对。

后来改成「笨工具」，只接收关键词，返回原始结果。智能判断的事情交给上层的技能做。

经验是，工具越笨越好，智能交给上层。

第三个坑是编排层太灵活。

一开始我们想让编排层也支持条件判断，如果 A 就走流程 X，否则走流程 Y。

结果发现条件一多，流程就乱了，调试变得很困难。

后来改成固定流程，条件判断放到技能层去做。编排层只管顺序执行。

经验是，骨架要硬，灵活性放到内核里。

---

跑了半年，我们的系统现在有 6 个业务域，19 个技能，35 个工具。

每天处理几千个任务，稳定性一直保持在 99% 以上。

最让我满意的是，团队协作效率很高。运营同学经常自己改技能的 Prompt，不用找工程师。工程师专注在加新工具和优化性能上。

---

聊聊几个认知。

第一，框架不是越强大越好。

开源框架功能很多，但你用到的可能只有 20%。剩下 80% 的复杂性全变成了你的负担。

简单的方案往往是最好的方案。

第二，AI 的角色应该被限定。

很多人对 Agent 的期待是「给个目标就能自己完成」。这个期待在现阶段是不现实的。

AI 的优势是处理模糊的、创造性的任务，比如写文案、做分析。AI 的劣势是做确定性的流程控制和错误处理。

把 AI 放在它擅长的位置，把它不擅长的事情交给传统代码。

第三，可控比智能更重要。

在生产环境里，一个「不太聪明但稳定可控」的系统，比一个「很聪明但不可预测」的系统有用得多。

用户需要的是解决问题，不是看 AI 表演。

---

最后说一下什么情况适合用开源框架，什么情况适合自己搭。

如果你是做 Demo、做 POC、快速验证想法，开源框架是好选择。能让你快速看到效果。

如果你是要做生产级的系统，需要稳定、可控、可迭代，建议还是自己设计架构。不需要多复杂，核心是想清楚确定性和灵活性的边界在哪里。

我们的方案不一定是最优的，但它解决了我们的问题。希望这些经验对你有参考价值。

有问题可以在评论区讨论，我们可以聊聊具体的实现细节。
