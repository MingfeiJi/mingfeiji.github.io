# RAG 召回准确率从 75% 到 90%：我做对了这三件事

"AI 怎么又答非所问了？"

这是我们客服 AI 上线后，收到最多的投诉。

用户问"怎么退票"，AI 回答的是"如何改签"。
用户问"价格是多少"，AI 回答的是"如何支付"。

问题出在哪？不是大模型不行，是 **RAG 召回不准**。

今天聊聊我们是怎么把 RAG 召回准确率从 75% 提升到 90% 的。

---

## 一、先搞清楚：RAG 召回为什么不准？

RAG（检索增强生成）的核心逻辑很简单：

```
用户问题 → 向量检索 → 召回相关文档 → 大模型生成回答
```

准确率不高，问题可能出在三个环节：

### 环节 1：向量化质量差

如果文档的向量化做得不好，相似度计算就不准。

常见问题：

- Embedding 模型选得不对
- 文档分块方式不合理
- 没有做预处理（去噪、归一化）

### 环节 2：检索策略单一

很多人用 RAG，就是简单地"向量相似度 Top K"。

但这种方式有个问题：**向量相似 ≠ 语义相关**。

"退票"和"改签"在向量空间里可能很近，但它们是完全不同的业务场景。

### 环节 3：知识库质量差

垃圾进，垃圾出。

如果知识库里的内容混乱、过时、冗余，再好的检索策略也没用。

---

## 二、第一件事：分层索引，先粗筛再精排

我们做的第一个优化是：**分层索引**。

### 原来的做法

```
用户问题 → 全库向量检索 → Top 10 → 送给大模型
```

问题：知识库有几万条文档，用户问"退票"，可能召回一堆"改签"、"投诉"、"价格"相关的内容，因为它们在向量空间里都挺近的。

### 优化后的做法

```
用户问题 → 意图分类 → 对应类目检索 → Top 5 → 送给大模型
```

我们把知识库分成了几个大类：

- 产品介绍
- 操作流程（订票、退票、改签……）
- 规则政策（价格、优惠、限制……）
- 常见问题

用户问题先做意图分类，判断属于哪个大类，再在对应类目下做检索。

**效果**：召回准确率从 75% 提升到 82%。

### 具体怎么做意图分类？

我们用了一个简单的方法：**关键词 + 语义**双重判断。

先用关键词规则做快速分类：

```python
if "退" in query or "取消" in query:
    category = "操作流程-退票"
elif "价" in query or "多少钱" in query:
    category = "规则政策-价格"
```

关键词匹配不上的，再用大模型做语义分类。

这样既保证了速度（关键词匹配很快），又保证了覆盖率（语义分类兜底）。

---

## 三、第二件事：混合检索，向量 + 关键词

第二个优化：**混合检索**。

### 纯向量检索的问题

向量检索擅长语义匹配，但对**精确匹配**不太行。

比如用户问"北京到上海的票价"，向量检索可能召回"上海到杭州的票价"，因为语义很接近。

但用户明明指定了"北京到上海"，你给他"上海到杭州"，肯定不对。

### 混合检索的做法

```
向量检索（语义匹配）
    ↓
关键词检索（精确匹配）
    ↓
结果融合 + 重排序
```

具体来说：

1. 向量检索召回 Top 20
2. 关键词检索召回 Top 20
3. 取两者的交集和并集，根据得分加权排序
4. 最终返回 Top 5

**关键词检索怎么做？**

我们用了 BM25 算法，这是一个经典的关键词检索算法。

简单说就是：用户问题里的关键词，在文档里出现得越多、越集中，得分越高。

**效果**：召回准确率从 82% 提升到 87%。

---

## 四、第三件事：差异化策略，不同知识不同处理

第三个优化：**差异化策略**。

我们发现，不同类型的知识，适合不同的检索策略。

### 类型 1：结构化数据

比如"不同城市的票价"。

这种数据是结构化的，应该用**精确匹配**，而不是向量检索。

我们的做法：

- 把票价数据存成结构化表格
- 用户问票价时，先解析出"出发地"、"目的地"
- 直接查表，不走向量检索

### 类型 2：时效性数据

比如"今天的限行政策"、"当前的促销活动"。

这种数据变化快，放在知识库里容易过时。

我们的做法：

- 不存知识库，直接调 API 实时查询
- 知识库只存"如何查询"的指引
- 返回时标注"数据来源：XX 系统，更新时间：XX"

### 类型 3：长尾 FAQ

比如"如何开发票"、"忘记密码怎么办"。

这种问题量大、覆盖长尾，适合用**向量检索 + 语义重排**。

我们的做法：

- 每个问题单独成段，方便召回
- 向量检索召回 Top 10
- 用大模型对召回结果做语义重排，选出最相关的 3 个

### 类型 4：核心方法论

比如"内容创作方法论"、"运营 SOP"。

这种知识非常重要，被频繁引用，必须 100% 准确。

我们的做法：

- 单独整理，设为最高召回优先级
- 意图匹配到后，直接返回，不走向量检索
- 人工定期 Review，确保内容准确

### 差异化策略的效果

应用差异化策略后，整体准确率从 87% 提升到 90%。

更重要的是，**不同类型问题的准确率都更稳定了**：

| 问题类型 | 优化前 | 优化后 |
|---------|-------|-------|
| 票价查询 | 72% | 95% |
| 政策查询 | 68% | 88% |
| 操作流程 | 80% | 92% |
| 长尾 FAQ | 78% | 86% |

## 五、一些细节优化

除了上面三件大事，还有一些细节优化，也很重要。

### 优化 1：文档分块策略

原来我们按固定长度分块（比如 500 字一块），效果不好。

后来改成**按语义分块**：

- 检测段落边界
- 保持标题和正文的关联
- 每个分块都带上标题作为上下文

分块质量提升后，召回准确率提升了约 3%。

### 优化 2：Query 改写

用户的问题有时候很口语化、很模糊。

比如"那个怎么弄"——"那个"是什么？"弄"是什么操作？

我们加了一个 Query 改写环节：

```
用户原始问题 → 大模型改写 → 改写后的问题 → 检索
```

改写的目标是：

- 补充缺失的上下文（根据对话历史）
- 把口语化表达转成规范表达
- 拆解复合问题

### 优化 3：负反馈学习

上线后，我们会收集用户的负反馈：

- 用户点了"没有帮助"
- 用户重复问同一个问题
- 用户直接转人工

这些负反馈会进入一个 Bad Case 库，我们每周 Review：

- 分析召回错误的原因
- 补充缺失的知识
- 优化检索策略

**持续迭代，比一次性优化更重要。**

## 六、一些血泪教训

### 教训 1：别迷信 Embedding 模型

很多人觉得换一个更好的 Embedding 模型，准确率就能大幅提升。

我们试过了：从 OpenAI 的 ada 换成 text-embedding-3-large，准确率只提升了 2%。

**Embedding 模型只是基础，检索策略和知识库质量更重要。**

### 教训 2：分块不是越小越好

一开始我们想：分块越小，召回越精准。

结果发现不对。

分块太小，会丢失上下文。用户问"怎么退票"，召回了一个只包含"点击确认"的分块，完全不知道是在说什么。

后来我们找到了平衡点：每个分块包含完整的一个知识点，通常是 200-500 字。

### 教训 3：召回数量不是越多越好

直觉上，召回 Top 20 应该比 Top 5 好，因为覆盖更全。

但实际测试发现，召回太多反而会"稀释"相关内容，大模型被无关信息干扰，生成质量下降。

我们最终的设置是：召回 Top 5，每个分块 300 字左右，总共 1500 字左右的上下文。

## 七、写在最后

RAG 看起来简单，做好很难。

**核心不是技术多先进，而是对业务的理解有多深。**

- 你要知道用户会问什么样的问题
- 你要知道不同类型的知识应该怎么处理
- 你要知道什么时候用向量检索，什么时候用精确匹配

这些都需要对业务的深入理解，不是调几个参数就能搞定的。

如果你也在做 RAG，希望这篇文章对你有帮助。

**记住：没有银弹，只有持续迭代。**
