## 写在前面

每次有人问我"大模型怎么落地"，我第一个问题永远是：你确定要用RAG吗？

不是所有场景都适合RAG，但如果你的场景是"让大模型基于特定知识库回答问题"，RAG几乎是唯一选择。

这篇文章会回答三个核心问题：
1. RAG是什么，为什么要用它？

## 一、先搞清楚：为什么是RAG？

### 1.1 大模型原生的四个硬伤

大模型很强，但有四个天生的缺陷：

**第一，时效性差。** 训练数据有截止日期，最新的消息它不知道。你问它"昨天OpenAI发布了什么"，它答不上来。

**第二，会幻觉。** 没把握的事情它会瞎编，而且编得特别自信。更可怕的是，你根本不知道它什么时候在瞎编。

**第三，专业性不足。** 通用大模型对垂直领域懂得不深，医疗、法律、金融这些专业领域，容易出错。

**第四，隐私安全。** 企业数据不敢往公有大模型里塞，怕泄露商业机密。

### 1.2 解决方案对比

解决这些问题有三种方案：

**方案一：模型微调（Fine-tuning）**

把你的专业数据喂给模型，让它"学会"这些知识。

问题是：
- 成本太高，一次微调动辄几十万
- 效果不稳定，微调完还是可能幻觉
- 数据更新了还得重新微调

**方案二：超长提示词（Long Context）**

把所有相关资料塞进提示词里，让模型基于这些内容回答。

问题是：
- 上下文窗口有限，塞不了太多
- 塞太多内容，中间部分最容易被遗忘（Lost in the Middle问题）
- 成本高，每次调用都要处理大量Token

**方案三：RAG（检索增强生成）**

把资料切成小块存起来，用户问问题时，先从里面找相关内容，再塞给模型生成答案。

优势：
- **省钱**：不用训练模型
- **专业**：答案基于你的资料，不瞎编
- **安全**：数据在你自己的知识库里，不怕泄露
- **灵活**：资料更新了直接替换，不用重新训练

**所以，如果你的场景是"让大模型基于特定知识库回答问题"，RAG几乎是唯一选择。**

## 二、RAG的核心原理

### 2.1 一句话解释RAG

RAG全称Retrieval-Augmented Generation，中文叫"检索增强生成"。

**说人话：给AI加个知识外挂。**

### 2.2 RAG的工作流程

```
用户提问
    ↓
Query处理（改写、补充）
    ↓
向量检索（从知识库找相关内容）
    ↓
结果重排序（筛选最相关的）
    ↓
组装Prompt（把检索结果 + 用户问题塞给大模型）
    ↓
大模型生成答案
    ↓
输出给用户
```

### 2.3 核心组件

**知识库（Knowledge Base）**

存储你所有的文档、FAQ、资料。需要做预处理：切片、向量化。

**向量数据库（Vector Database）**

存储向量化后的文档片段。支持高效的相似性搜索。常用的有Milvus、Pinecone、Qdrant等。

**Embedding模型**

把文本转换成向量。常用的有OpenAI的text-embedding-3、BGE等。

**大模型（LLM）**

基于检索结果生成最终答案。可以用GPT-4、Claude、国产模型等。

## 三、知识库构建：90%的人在第一步就错了

### 3.1 我踩过的第一个坑：没想清楚分类就开始采集

第一个项目，我们采集了10万条FAQ数据，兴冲冲地做向量化、建索引。

结果一测试，效果惨不忍睹。

问题出在哪？**数据本身就是一团乱麻。**

同一个问题有十种不同的表述，不同类型的问题混在一起，噪音比信号还多。

**教训：先定分类体系，再采集数据。**

### 3.2 分类体系怎么定？

两个原则：

**原则一：业务导向**

分类要匹配用户的真实提问方式，不是你觉得应该怎么分。

去看用户实际问的问题，按他们的思维方式分类。

**原则二：MECE原则**

相互独立、完全穷尽。避免一条数据属于多个分类，也不能有遗漏。

### 3.3 数据采集：内部数据优先

数据来源分两类：

**企业内部数据（优先）**
- 业务系统沉淀的结构化数据
- 客服聊天记录、工单
- 会议纪要、内部文档
- 已有的FAQ库

**公开外部数据（补充）**
- 搜索引擎可访问的内容
- 行业报告、百科内容
- 竞品公开资料

**一个原则：内部数据的价值远高于外部数据。** 因为内部数据反映的是你业务的真实场景，外部数据只能做通用补充。

### 3.4 我踩过的第二个坑：切片策略没想清楚

知识库数据量大了之后，必须切片。

一开始我们用固定长度切片，每500字切一段。结果发现：

- 经常在句子中间切断，语义不完整
- 关键信息被分到两个片段里，检索时找不全
- 有些段落太短，噪音太多

### 3.5 正确的切片策略

**策略一：按语义切片**

以段落、章节为单位，保证每个片段语义完整。

不要机械地按字数切，要按内容的逻辑边界切。

**策略二：控制长度**

推荐1000-3000字符。

太短噪音多，太长检索不精准。

**策略三：保留重叠**

片段之间保留10-20%的重叠，避免关键信息被切断。

比如一个2000字的段落，切成两个1200字的片段，中间有400字的重叠。

### 3.6 数据质量检查清单

切片完成后，做一轮质量检查：

- [ ] 每个片段语义是否完整？
- [ ] 关键信息是否被切断？
- [ ] 是否有重复或冗余的片段？
- [ ] 片段长度分布是否合理？

## 四、检索模块：Query改写是被忽视的关键

### 4.1 很多人花大量时间在错误的地方

我见过很多人花大量时间优化向量检索、调参数，效果还是不好。

问题往往出在最上游：**用户的问题本身就没处理好。**

### 4.2 用户的问题永远是模糊的

真实用户不会问"请介绍一下你们产品的退款政策"。

他们会问：
- "怎么退"
- "钱什么时候到"
- "上次那个订单能退吗"

这些问题直接丢给检索模块，根本找不到相关内容。

### 4.3 Query改写是什么？

在检索之前，先把用户的问题优化一遍：

**1. 补充上下文**

用户说"这个产品"，补充成具体产品名。

**2. 消除歧义**

"苹果"是水果还是公司？根据上下文判断。

**3. 拆分多意图**

"帮我查天气和订机票"→ 拆成两个独立查询。

**4. 转成精准检索词**

模糊表达 → 具体关键词。

"怎么退" → "退款流程 退款政策 申请退款"

### 4.4 这一步产品经理能直接上手

很多人不知道，Query改写本质上就是数据标注工作。

你需要做的是：
1. 收集真实用户的问题
2. 分析用户的真实意图
3. 定义改写规则
4. 积累badcase持续优化

**不需要懂算法，只需要理解业务场景。**

### 4.5 Query改写的实现方式

**方式一：基于规则**

定义关键词映射、同义词替换等规则。

优点：可控、稳定
缺点：规则维护成本高

**方式二：基于LLM**

让大模型理解用户意图，生成优化后的查询。

优点：智能、灵活
缺点：成本高、延迟增加

**我的实践：两者结合**

常见问题用规则处理，保证速度和稳定性。复杂问题用LLM处理，提高准确性。

## 五、检索参数怎么调？

### 5.1 核心参数

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| 召回数量（Top-K） | 3-10条 | 太少可能漏掉相关内容，太多会引入噪音 |
| 匹配度阈值 | 0.7-0.95 | 低于阈值的结果过滤掉，根据业务场景调整 |
| 检索方式 | 混合检索 | 语义检索 + 关键词检索结合 |

### 5.2 语义检索 vs 关键词检索

**语义检索**

适合模糊匹配。用户问"怎么退钱"能找到"退款流程"。

原理：把查询和文档都转成向量，计算相似度。

**关键词检索**

适合精确查询。用户问"订单号12345"必须精确匹配。

原理：基于关键词匹配，类似传统搜索引擎。

**实际项目中，两种方式结合效果最好。**

### 5.3 混合检索的策略

```
用户Query
    ↓
语义检索 → 得到Top-K结果 → 分数0.8, 0.75, 0.7...
关键词检索 → 得到Top-K结果 → 分数0.9, 0.6, 0.5...
    ↓
结果融合（加权或RRF算法）
    ↓
最终排序结果
```

融合策略有很多种，最简单的是加权平均，效果好的是RRF（Reciprocal Rank Fusion）。

## 六、答案生成的提示词设计

### 6.1 必须包含的要素

**要素一：角色定义**

明确AI的身份和职责。

```
你是[公司名]的客服专家，负责回答用户关于产品使用的问题。
```

**要素二：回答依据**

强调只基于提供的内容回答，不要编造。

```
请严格基于以下检索结果回答用户问题。如果检索结果中没有相关信息，请明确告知用户"抱歉，我暂时无法回答这个问题"。
```

**要素三：无答案处理**

如果检索结果无法回答，要明确告知，不要瞎编。

**要素四：格式要求**

分点、用列表、标注来源，让答案结构清晰。

```
请用以下格式回答：
1. 直接回答用户问题（1-2句话）
2. 详细解释（如有必要）
3. 相关建议（如有必要）
4. 信息来源标注
```

### 6.2 完整的提示词模板

```
## 角色
你是[公司名]的智能客服助手，负责基于公司知识库回答用户问题。

## 任务
根据用户的问题和检索到的相关内容，生成准确、有帮助的回答。

## 规则
1. 只基于检索结果回答，不要编造信息
2. 如果检索结果无法回答问题，请说"抱歉，我暂时无法回答这个问题，建议联系人工客服"
3. 回答要简洁明了，避免废话
4. 如果问题涉及多个方面，请分点回答

## 检索结果
{检索到的内容}

## 用户问题
{用户的问题}

## 请回答：
```

## 七、效果评估：别只看准确率

### 7.1 完整的评估指标

很多人只关注"答案对不对"，这是不够的。

**指标一：准确率**

答案正确的比例。这是最基础的指标。

**指标二：召回率**

能回答的问题比例。很多人忽略这个指标。

如果RAG系统对50%的问题说"无法回答"，召回率就太低了。

**指标三：响应时间**

用户等多久能得到答案。

一般要求3秒内响应，超过5秒用户体验就很差了。

**指标四：幻觉率**

瞎编的比例。这是最需要关注的。

宁可说"不知道"，也不能瞎编。

### 7.2 建立测试集

至少准备100个测试问题：
- 覆盖各类问题类型
- 包含边界case
- 包含一些"知识库里没有"的问题

**持续更新测试集**，每发现一个badcase，就加入测试集。

### 7.3 建立badcase收集机制

```
用户反馈 → 标记badcase → 分类标注原因 → 定向优化
```

**每周复盘一次：**
- 这周有多少badcase？
- 问题主要出在哪个环节？（检索不准？生成幻觉？Query理解错误？）
- 针对性优化

## 八、常见问题及解决方案

### 8.1 检索不准

**现象：** 用户问的问题和检索到的内容不相关

**可能原因：**
1. Query改写没做好
2. 切片策略不合理，相关内容被切断
3. Embedding模型效果差
4. 检索参数设置不当

**解决方案：**
1. 优化Query改写规则
2. 调整切片策略，增加重叠
3. 尝试更好的Embedding模型
4. 调整Top-K和阈值参数

### 8.2 答案幻觉

**现象：** 答案看起来合理，但实际上是编的

**可能原因：**
1. 提示词没有强调"不要编造"
2. 检索结果不够，模型"脑补"了
3. 模型本身的问题

**解决方案：**
1. 强化提示词约束
2. 降低模型Temperature
3. 增加"无答案"的处理逻辑
4. 人工审核机制

### 8.3 响应太慢

**现象：** 用户等待时间太长

**可能原因：**
1. 向量检索慢
2. 大模型推理慢
3. Query改写增加了额外延迟

**解决方案：**
1. 优化向量数据库索引
2. 使用更快的模型或API
3. 缓存常见问题的答案
4. 异步处理 + 流式输出

## 九、最后的建议

### 9.1 先跑通MVP，再优化

不要一开始就追求完美。先用最简单的方案验证可行性：

1. 用现成的RAG框架（Dify、FastGPT）
2. 准备100条测试数据
3. 跑通最基本的流程
4. 收集反馈，定向优化

### 9.2 数据质量 > 技术方案

花在清洗数据上的时间，永远比调参数值。

一个干净的知识库 + 简单的技术方案，效果往往比脏数据 + 复杂方案好得多。

### 9.3 产品经理要懂技术

不需要会写代码，但要理解每个环节的原理和边界：

- 知道切片为什么重要
- 知道Query改写能解决什么问题
- 知道检索参数怎么调
- 知道幻觉怎么产生的

**这样才能和技术团队有效沟通，才能做出正确的产品决策。**

### 9.4 持续迭代

RAG不是一次性项目，需要持续优化：

1. 每周分析badcase
2. 每月更新知识库
3. 每季度评估整体效果
4. 持续跟进新技术

## 十、总结

RAG知识库落地的核心要点：

1. **先想清楚要不要用RAG** —— 不是所有场景都适合
2. **数据分类先行** —— 先定分类体系，再采集数据
3. **切片策略要合理** —— 按语义切，保留重叠
4. **Query改写是关键** —— 最容易被忽视，产品经理能直接上手
5. **混合检索效果好** —— 语义 + 关键词结合
6. **提示词要约束** —— 强调不要编造，无答案要明说
7. **评估要全面** —— 准确率、召回率、响应时间、幻觉率
8. **持续迭代** —— 建立badcase收集和优化机制
