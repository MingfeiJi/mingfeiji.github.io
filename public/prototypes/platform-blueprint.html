PLATFORM BLUEPRINT · 产品形态决策

平台总蓝图 & 产品形态决策

把灵感、资产库、创作、剪辑、审核、复盘 + 副驾，作为一个平台统一拆解：所有对象、所有用户路径、整套架构结构化放好，最后给一个明确的整体产品形态决策——它到底应该长成"几个独立工具"、"一个巨型后台"，还是别的。

01

产品本质判断

一句话：用户带着【一个内容意图】进入，平台用【发现 → 沉淀 → 创作 → 成片】这条人机协作流水线，把【全网爆款 / 素材 / 想法】转成【可发布的图文 / 视频】，并通过【表现回流】沉淀成爆款配方，越用越聪明。

核心闭环：发现 → 沉淀 → 创作 → 成片 → 复盘（回流反哺发现）。最高频任务：找到与我相关的爆款、把好片段沉成可复用素材、把素材+脚本批量出成片。最核心对象：素材资产（唯一真源）、灵感（爆款）、草稿/成片、创作篮、爆款配方。

06

整体产品形态决策 ★

这是这份蓝图要拍的板
决策结论
做成「共享底座上的旅程式多工作台平台」——一个平台、一套通用承载件、一个素材真源、一个常驻副驾；前端是按旅程的几个工作台视图，用旅程导航无缝串成一条动线、带上下文流转。

不是六个各自为站的独立工具（割裂、重复造、丢上下文），也不是一个塞满菜单的巨型后台（认知过载），更不是把所有事压进单一大画布（角色冲突、太挤）。模块是"视图"，不是"系统"；单个 AI 能力是"动作"，不是"页面"。

三个候选方案的权衡
候选描述优劣适配
A · 六个独立工具每个模块各做一个产品/站点各自简单、好起步割裂、重复造轮子、跨模块丢上下文、像六个系统低
B · 单一融合大画布所有事都在一个画布里完成极致连续角色需求冲突、认知过载、难维护、移动端崩中低
C · 共享底座 + 旅程式多工作台 (推荐)几个专门工作台共享承载件/真源/副驾，旅程串联、带上下文既连续又不挤、按角色聚焦、底座解耦好维护、加功能走配置需治理契约与统一规范高
为什么选 C
  • 角色差异大：编导找灵感、剪辑取片段、投放看数据——需求不同，硬塞一个画布会互相干扰，所以要专门视图。
  • 认知负荷：平台功能很多，一个页面承载不了；分成旅程阶段，每屏只承载一段任务。
  • 连续性不丢：靠统一承载件 + 旅程导航 + 带上下文跳转 + 常驻副驾 + 同一素材真源，几个视图仍像"一个产品"，而不是六个。
  • 工程可持续：底座（承载件/能力/真源）解耦，各视图可独立演进；前端↔能力走可配置契约，加功能不动前端。
配套决策规则（什么放哪）

该成为「工作台视图」

  • 一个旅程阶段的主场景（找灵感 / 攒素材 / 创作 / 成片 / 复盘）
  • 有独立浏览 / 组织需求的对象集合（灵感卡流、素材库）

该成为「上下文动作」（不开页）

  • 对选中对象的 AI 能力：切片 / 改编 / 裂变 / 召回 / 改写
  • 单步、即时、跟对象强绑定的操作

该进「任务中心」（后台异步）

  • 耗时 / 批量：爬取、切片、向量化、批量生成
  • 需要进度、成本、失败重试的

该是「全局贯穿件」

  • 副驾、意图框 / 搜索、创作篮、任务中心入口
  • 跟着用户走、在哪个视图都在
07

AI 嵌入 & 副驾

AI 是副驾不是工具站：选中即用（动作长在卡上）·结果回流真源（生成物自动成资产/草稿卡）·可解释 / 可干预 / 可回退（归因、改切点换素材、血缘版本）·批量进任务中心·成本/额度可见·推荐说明理由。TripYoYo 作为常驻 Agent 贯穿，能对话式编排整条流程、人审收口。

平台 MVP / P1 / P2

P0 · 跑通主动线

  • 灵感工作台（洞察卡流）+ 资产库（真源 + 检索 + 切片入库）

P1 / P2

  • P2：副驾 Agent 编排 · 反馈闭环 / 爆款配方 / 推荐 · 浏览器 skill（低风险机械活儿）· 跨项目治理
  • 暂不做：养号 / 发布
